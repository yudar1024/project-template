# 模块详细展开（Part 1/3）：项目元信息 & 需求描述

> 贯穿示例项目：**task-flow** — 面向小型团队的任务管理系统

---

## 模块一：项目元信息

### 1. 模块目标

项目元信息是 Agent 建立**全局认知**的基础。它决定了 Agent 后续所有决策的"基调"：
- **项目规模**影响架构复杂度（单体 vs 微服务）
- **目标平台**决定技术选型方向（Web/Mobile/CLI）
- **目标用户**影响 UI/UX 风格和性能优化方向

### 2. 核心理念

1. **一句话定位**：项目简述应能让任何人在 5 秒内理解项目做什么
2. **规模决定架构**：明确规模就是在告诉 Agent "不要过度设计"或"必须考虑扩展性"
3. **用户画像驱动决策**：面向内部运营 vs 面向 C 端用户，技术决策截然不同

### 3. 字段详解

#### 项目名称

| 维度 | 说明 |
|------|------|
| 格式要求 | 英文 kebab-case，简短、有意义 |
| ✅ 优秀 | `task-flow`、`inventory-hub`、`log-analyzer` |
| ❌ 不良 | `my-app`、`test`、`project1`、`新系统` |
| 要点 | 名称会成为代码仓库名、包名前缀、部署标识，应反映项目用途 |

#### 项目简述

| 维度 | 说明 |
|------|------|
| 格式要求 | 一句话，包含"给谁用"+"做什么"+"核心特点" |
| ✅ 优秀 | 面向小型团队的任务管理系统，支持看板视图、任务分配和进度追踪 |
| ❌ 不良 | 一个管理系统 |
| 要点 | 避免"xx平台"这种空泛表达，要说清核心能力 |

#### 项目规模

| 规模 | 判定标准 | 架构暗示 | 典型周期 |
|------|---------|---------|---------|
| 小型 | 1-5 个核心功能，单一职责 | 单文件或简单分层 | 1-3 天 |
| 中型 | 5-20 个功能，有持久化和认证 | 分层架构，前后端分离 | 1-4 周 |
| 大型 | 20+ 功能，多业务域 | 领域驱动，可能微服务 | 1-6 月 |

#### 目标平台

不仅写"Web"，还要说明具体形态：

| ✅ 精确 | ❌ 模糊 |
|---------|---------|
| Web SPA（React）+ RESTful API Server（独立部署） | Web |
| Cross-platform Desktop (Electron) | 桌面应用 |
| CLI 工具（支持管道操作和 JSON 输出） | 命令行 |
| Android/iOS (React Native) + BFF 层 | 移动端 |

#### 目标用户

| ✅ 精确 | ❌ 模糊 |
|---------|---------|
| 5-30 人研发团队的项目经理和开发人员，有基本技术素养 | 所有人 |
| 仓库管理员（非技术人员，需要简洁界面） | 用户 |
| 后端运维工程师，熟悉命令行操作 | 技术人员 |


## 模块二：需求描述

### 1. 模块目标

需求描述是整个输入的**核心中枢**。它回答"做什么"和"做到什么程度"。模糊的需求是 Agent 产出低质量代码的首要原因——不是 Agent 能力不足，而是它不得不"猜测"你的意图。

### 2. 核心理念

1. **验收条件是灵魂**：功能不写验收条件 = 没写需求。验收条件是唯一消除歧义的手段
2. **业务背景提供决策依据**：Agent 遇到技术取舍时，会参考业务背景做判断
3. **数据模型是契约**：明确的数据模型防止 Agent 自行设计不合理的表结构
4. **业务规则最容易遗漏**：80% 的 BUG 来自未说明的业务规则

### 3. 字段详解

#### 3.1 业务背景

**核心公式**：`现状痛点 → 期望目标 → 衡量标准`

| ✅ 优秀写法 | ❌ 不良写法 |
|------------|-----------|
| ① 描述现状和痛点 | 做一个任务管理系统 |
| ② 明确要达到的目标 | |
| ③ 给出可量化的成功标准 | |

**优秀示例**：
```
团队目前使用微信群和 Excel 管理任务，存在以下痛点：
1. 任务状态不透明 — 经常出现两人同时做同一件事
2. 优先级频繁变化但没有记录 — 无法追溯决策原因
3. 无工作量统计 — 月度汇报靠回忆，数据不准确

目标：
- 所有任务在线可视化管理，任务状态实时同步
- 所有操作留痕，支持历史追溯
- 自动生成工作量统计报表

成功标准：
- 团队成员每日使用率 > 80%
- 任务重复处理事件降低 90%
- 月度汇报准备时间从 2 天缩短到 30 分钟
```

#### 3.2 功能需求 — 用户故事

**格式**：`作为 <角色>，我希望 <做什么>，以便 <达到什么目的>`

**三要素缺一不可**：

| 要素 | 作用 | 示例 |
|------|------|------|
| 角色 | 明确谁在用这个功能 | 项目管理员、普通成员、系统管理员 |
| 行为 | 明确做什么操作 | 创建任务并指定负责人 |
| 价值 | 明确为什么需要这个功能 | 让负责人知道自己要做什么 |

**写不好用户故事的三个典型错误**：

```
❌ 错误1：没有角色区分
"用户可以管理任务"
→ 哪种用户？管理员和普通成员的权限一样吗？

❌ 错误2：没有验收条件
"F-001 | 用户登录 | 实现登录功能 | — | P0"
→ 密码规则是什么？错误处理怎么做？Token 有效期多久？

❌ 错误3：验收条件不可测试
"F-001 | 用户登录 | ... | 登录速度要快 | P0"
→ "快"是多快？200ms？1s？5s？
```

#### 3.3 验收条件 — SMART 原则

每条验收条件都应符合：

| 原则 | 含义 | ✅ 正确 | ❌ 错误 |
|------|------|--------|--------|
| Specific | 具体 | 密码至少 8 位，含大小写字母和数字 | 密码要安全 |
| Measurable | 可度量 | 响应时间 < 300ms | 响应要快 |
| Achievable | 可实现 | 支持 100 并发用户 | 支持无限用户 |
| Relevant | 相关 | 登录失败返回"用户名或密码错误" | 登录页要好看 |
| Testable | 可测试 | 连续 5 次错误锁定账户 30 分钟 | 防暴力破解 |

#### 3.4 数据模型

**推荐描述层次**：

```
层次1：实体清单（有哪些核心对象）
层次2：字段定义（每个对象有哪些属性、类型、约束）
层次3：实体关系（对象之间的关联：1:1 / 1:N / N:N）
层次4：索引建议（高频查询字段的索引需求）
```

**字段描述规范**：

```
格式：字段名: 类型, 约束条件, 业务说明

✅ email: varchar(100), 唯一, 非空, 用于登录和通知
✅ status: enum(TODO, IN_PROGRESS, DONE), 非空, 默认 TODO

❌ email: string  （缺少长度、约束、业务含义）
❌ status: int    （不知道取值范围和含义）
```

#### 3.5 业务规则

**识别业务规则的检查清单**：

- [ ] 是否有字段值的合法范围？（如：金额 > 0）
- [ ] 是否有状态流转约束？（如：TODO → IN_PROGRESS → DONE）
- [ ] 是否有操作权限约束？（如：只有管理员能删除）
- [ ] 是否有数量限制？（如：每人最多参与 10 个项目）
- [ ] 是否有时间约束？（如：截止日期不能早于创建日期）
- [ ] 是否有唯一性约束？（如：同项目下任务标题不重复）
- [ ] 是否有级联操作？（如：删除项目时同步删除所有任务）
- [ ] 是否有并发冲突处理？（如：两人同时修改同一个任务）

#### 3.6 非功能需求

**常被遗忘的非功能需求**：

| 类别 | 需要明确的内容 |
|------|--------------|
| 性能 | 平均/峰值响应时间、并发用户数、数据量预估 |
| 安全 | 认证方式、鉴权粒度、数据加密、OWASP Top 10 |
| 可用性 | SLA 等级、故障恢复时间、数据备份策略 |
| 兼容性 | 浏览器版本、屏幕尺寸、国际化需求 |
| 可观测性 | 日志级别、监控指标、告警规则 |

### 4. 完整示例（task-flow）

```markdown
## 二、需求描述

### 2.1 业务背景

团队目前使用微信群和 Excel 管理任务，痛点如下：
1. 任务状态不透明 — 经常出现两人同时处理同一任务（月均 3-5 次）
2. 优先级变化无记录 — 事后追溯决策原因困难
3. 无工作量统计 — 月度汇报依赖人工统计，耗时 1-2 天且数据不准

本系统目标：
- 任务状态实时同步，消除信息不对称
- 所有操作留痕，支持审计和追溯
- 自动生成工作量统计，月度报表 30 分钟内完成

### 2.2 功能需求

#### 核心功能（MVP）

| 编号 | 功能名称 | 用户故事 | 验收条件 | 优先级 |
|------|---------|---------|---------|--------|
| F-001 | 用户注册 | 作为新团队成员，我希望通过邮箱注册账号，以便加入团队的任务管理系统 | 1. 邮箱格式校验（含@和域名）；2. 密码 ≥ 8位，含大小写字母和数字；3. 邮箱不可重复注册；4. 注册成功后自动登录 | P0 |
| F-002 | 用户登录 | 作为已注册用户，我希望通过邮箱和密码登录系统 | 1. 正确凭证→登录成功、返回 JWT Token（有效期 24h）；2. 错误凭证→提示"邮箱或密码错误"；3. 连续 5 次错误→锁定 30 分钟；4. Token 过期→返回 401 | P0 |
| F-003 | 项目创建 | 作为团队负责人，我希望创建项目并邀请成员 | 1. 必填：项目名称（2-50字符）；2. 选填：项目描述（≤500字符）；3. 创建者自动成为项目 ADMIN；4. 可通过邮箱邀请成员 | P0 |
| F-004 | 任务看板 | 作为项目成员，我希望以看板形式查看项目任务 | 1. 默认看板列：待办/进行中/已完成；2. 拖拽任务可改变状态和排序（乐观更新、失败回滚）；3. 各列显示任务数量；4. 支持自定义看板列名称 | P0 |
| F-005 | 任务管理 | 作为项目成员，我希望创建、编辑和查看任务 | 1. 必填：标题（2-200字符）、优先级；2. 选填：描述（Markdown，≤5000字符）、负责人、截止日期、标签（≤5个）；3. 支持按负责人/优先级/标签/关键词筛选；4. 任务详情页显示完整信息和操作记录 | P0 |
| F-006 | 任务删除 | 作为项目管理员，我希望删除不需要的任务 | 1. 仅 ADMIN 角色可删除；2. 删除需二次确认弹窗；3. 删除后在操作记录中保留痕迹 | P0 |

#### 扩展功能

| 编号 | 功能名称 | 简述 | 优先级 |
|------|---------|------|--------|
| F-101 | 任务评论 | 在任务详情页发表评论，支持 @提及成员 | P1 |
| F-102 | 统计仪表盘 | 任务完成趋势图、成员工作量分布（柱状图+饼图） | P1 |
| F-103 | 消息通知 | 被分配任务、任务状态变更时站内通知 | P2 |
| F-104 | 项目归档 | 项目完成后归档，归档后只读，可恢复 | P2 |

### 2.3 非功能需求

- **性能**：API 平均响应 < 300ms；看板页首屏加载 < 2s（首次）、< 500ms（缓存后）
- **安全**：JWT 身份认证 + 项目级角色鉴权；密码 BCrypt 存储；
  所有 API 接口鉴权（除注册/登录外）；防 XSS、CSRF
- **兼容性**：Chrome 120+ / Firefox 120+ / Edge 120+；
  最小支持宽度 1280px，推荐 1920px
- **可观测性**：关键操作写入审计日志（操作人、时间、变更内容）

### 2.4 数据模型

**用户（User）**
- id: bigint, 主键, 自增
- email: varchar(100), 唯一, 非空, 用于登录标识
- password_hash: varchar(255), 非空, BCrypt 加密
- nickname: varchar(50), 非空, 显示名称
- avatar_url: varchar(500), 可空, 头像地址
- status: enum(ACTIVE, LOCKED), 非空, 默认 ACTIVE
- login_fail_count: int, 默认 0, 连续登录失败次数
- locked_until: datetime, 可空, 锁定截止时间
- created_at: datetime, 非空
- updated_at: datetime, 非空

**项目（Project）**
- id: bigint, 主键, 自增
- name: varchar(100), 非空
- description: text, 可空
- owner_id: bigint, 外键→User.id, 非空, 创建者
- status: enum(ACTIVE, ARCHIVED), 非空, 默认 ACTIVE
- created_at, updated_at: datetime

**项目成员（ProjectMember）**
- project_id: bigint, 外键→Project.id
- user_id: bigint, 外键→User.id
- role: enum(ADMIN, MEMBER), 非空
- joined_at: datetime
- 联合主键: (project_id, user_id)

**看板列（BoardColumn）**
- id: bigint, 主键, 自增
- project_id: bigint, 外键→Project.id
- name: varchar(50), 非空, 列名称
- position: int, 非空, 排序位置
- 唯一约束: (project_id, name)

**任务（Task）**
- id: bigint, 主键, 自增
- title: varchar(200), 非空
- description: text, 可空, Markdown 格式
- project_id: bigint, 外键→Project.id, 非空
- column_id: bigint, 外键→BoardColumn.id, 非空
- assignee_id: bigint, 外键→User.id, 可空
- creator_id: bigint, 外键→User.id, 非空
- priority: enum(LOW, MEDIUM, HIGH, URGENT), 非空, 默认 MEDIUM
- due_date: date, 可空
- position: int, 非空, 列内排序
- created_at, updated_at: datetime
- 索引: project_id, assignee_id, priority

**任务标签（TaskTag）**
- task_id: bigint, 外键→Task.id
- tag_name: varchar(30), 非空
- 联合主键: (task_id, tag_name)

**操作记录（ActivityLog）**
- id: bigint, 主键, 自增
- project_id: bigint, 外键→Project.id
- task_id: bigint, 外键→Task.id, 可空
- user_id: bigint, 外键→User.id, 操作人
- action: varchar(50), 非空, 如 TASK_CREATED / STATUS_CHANGED
- detail: json, 可空, 变更前后的值
- created_at: datetime

**实体关系**：
- User 1:N ProjectMember（一个用户加入多个项目）
- Project 1:N ProjectMember（一个项目有多个成员）
- Project 1:N BoardColumn（一个项目有多个看板列）
- Project 1:N Task（一个项目有多个任务）
- BoardColumn 1:N Task（一个列有多个任务）
- User 1:N Task (assignee)（一个用户可被分配多个任务）
- User 1:N Task (creator)（一个用户可创建多个任务）
- Task 1:N TaskTag（一个任务有多个标签）
- Project 1:N ActivityLog（审计日志按项目归属）

### 2.5 业务规则

| 编号 | 规则 | 触发条件 | 处理逻辑 |
|------|------|---------|---------|
| BR-001 | 项目权限隔离 | 所有任务/成员操作 | 非项目成员访问返回 403 |
| BR-002 | 角色权限控制 | 删除任务/管理成员/修改项目 | 仅 ADMIN 角色可执行，MEMBER 角色返回 403 |
| BR-003 | 登录锁定 | 连续 5 次密码错误 | 锁定账户 30 分钟，期间即使密码正确也拒绝登录 |
| BR-004 | 默认看板列 | 创建项目时 | 自动创建"待办""进行中""已完成"三个看板列 |
| BR-005 | 看板列约束 | 删除看板列 | 列下有任务时禁止删除，提示"请先移走该列中的任务"|
| BR-006 | 任务标签上限 | 添加标签时 | 单个任务最多 5 个标签，超出提示"标签数量已达上限" |
| BR-007 | 截止日期约束 | 设置截止日期 | 截止日期不能早于当天 |
| BR-008 | 操作审计 | 任务创建/修改/删除/状态变更 | 自动写入 ActivityLog，记录操作人、时间和变更详情 |
| BR-009 | 项目归档 | 归档项目 | 归档后项目及其所有任务变为只读，API 返回 403 |
| BR-010 | 创建者不可移除 | 移除项目成员 | 项目创建者（owner）不可被移除，也不可降级为MEMBER |

### 2.6 外部接口

本项目无需对接外部系统，所有数据自包含。
未来 P2 迭代可能对接邮件服务发送通知（暂不实现）。
```
